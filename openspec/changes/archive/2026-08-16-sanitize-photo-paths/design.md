## Context

`Database._foto(foto_id)` returns `os.path.join(self.fotos_dir, foto_id)` with no validation. A photo id like `../../etc/foo` makes the resolved path escape `fotos_dir`. `_replace_fotos` then calls `open(path, "wb")` on that path, writing a file outside the photos directory. Verified in testing.

## Goals / Non-Goals

**Goals:**
- Photo files can only be written inside the configured photos directory.
- Traversal ids are rejected, not silently rewritten to a different name.

**Non-Goals:**
- Changing how valid photo ids are stored (plain ids keep working unchanged).
- Sanitizing client ids that are merely unusual but safe (e.g. dots in the middle).

## Decisions

**D1 — Validate the photo id at the model boundary.**
- Add a Pydantic validator on `FotoIn.id` that rejects ids containing `/`, `\`, or `..`.
- *Rationale*: rejecting at the schema layer stops traversal before any file I/O and surfaces a clear 422; it also covers both push and any future path that carries `FotoIn`.
- *Alternative considered*: only validating in `_foto`/`_replace_fotos` — rejected because it would still allow a write attempt before failing, and would leave other `FotoIn` consumers unprotected.

**D2 — Belt-and-braces check at the file layer.**
- In `_foto`, resolve the candidate path and ensure its real (or normalized) path stays within `fotos_dir`; raise if it does not.
- *Rationale*: defense in depth; if a future id source bypasses the model, the file layer still refuses to escape.

**D3 — Files touched.**
- `app/models.py` (`FotoIn.id` validator), `app/database.py` (`_foto` containment check), `test_main.py` (traversal and normal-id cases).

## Risks / Trade-offs

- [Rejecting `..` in an id] → Client photo ids are generated by the app as UUIDs/filenames, so no legitimate id contains `..`; rejecting is safe.

## Migration Plan

None — additive validation; existing stored photo ids (plain filenames) are unaffected.
