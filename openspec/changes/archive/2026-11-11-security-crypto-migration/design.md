# Design: Android Keystore settings storage

## Decisions

### Direct Android Keystore instead of Tink

The app only needs to encrypt three short strings. A direct AES-256-GCM key in
`AndroidKeyStore` avoids adding a dependency while keeping the key material
inside the Keystore.

- Alias: `elisdb_settings_aes_v1`.
- Key generation: `KeyGenParameterSpec` with AES/GCM/NoPadding, 256-bit key and
  randomized encryption (the IV comes from the cipher).
- Preferences: `elisdb_settings_keystore`, separate from the legacy file.
- Value format: `v1:<base64(iv)>:<base64(ciphertext)>`, so the format can evolve
  without reusing an IV.

### Safe, idempotent migration

Migration runs on first read/write when the new preferences file is empty:

1. Read legacy values (plaintext keys first, then `EncryptedSharedPreferences`).
2. Encrypt and write all three values with `commit()`.
3. Read them back and compare.
4. Only after a successful verification, clear the legacy copies.

Failures leave the legacy data intact and make `save()` throw
`SecureStorageUnavailable`; `settings()` continues to read the legacy data
read-only. Running the migration again is safe.

## Risks / Trade-offs

- A Keystore failure or invalidation (OEM, device transfer) can make the old key
  unreadable; the user then has to reimport `<user>.config.json`. The fail-safe
  path keeps legacy data readable where possible and never deletes before
  verification.
- Legacy `security-crypto` remains as a read-only path during the migration
  window and can be removed in a later change.
- The custom format must keep the IV unique per write; it is generated by the
  cipher and stored alongside the ciphertext.

## Verification

- Unit build and instrumented `KeystoreSettingsStoreTest` cover roundtrip,
  ciphertext-at-rest, plaintext migration, encrypted migration, and fail-closed
  behavior when the Keystore key is unavailable.
